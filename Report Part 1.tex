\section{Section 1 -- Traditional Machine Learning Workflow and Ethics (Dataset 1)}

\noindent\textit{Dataset~1 is binary prediction of professional CSGO match winners from team- and player-level pre-match statistics.} Match outcomes are hard to predict from pre-match rows alone: fifty per cent is guessing, and low-sixties accuracy is already strong; similar work sometimes reaches about sixty-five per cent when neural models or extra context are added. The section covers cleaning, EDA, linear and tree models, CatBoost, K-Means as a sanity check, tuning, feature importance, and a short ethics discussion. Numbers below are on a held-out test set; leakage columns are stripped before training.

\paragraph{Introduction and Objectives.}
The work follows a standard supervised pipeline on tabular match data: define the task, clean the rows, explore patterns, fit several model families, and state clearly what the scores do and do not mean. The emphasis is practical---imputation choices, engineered fields, which models gain accuracy---rather than chasing an isolated leaderboard number. The aim is accuracy clearly above random (50\%) with interpretable models, and an explicit account of where the data and the task fall short.

The implementation uses Python (pandas, NumPy, scikit-learn). Seeds are fixed where it matters so splits and grid searches can be replayed. The inputs are clean columns; the outcomes are not---matches stay partly random even when the features look sensible.

\subsection{1.1\quad Dataset Selection and Problem Definition}

\subsubsection{1.1.1\quad Dataset Overview}

The \textbf{CSGO Match Prediction} set is historical pro matches with team- and player-level pre-match fields (Kaggle: \url{https://www.kaggle.com/datasets/gabrieltardochi/counter-strike-global-offensive-matches}). The file \texttt{csgo\_games.csv} is included with the coursework submission. Raw: three thousand seven hundred and eighty-seven rows, one hundred and seventy columns; after cleaning and engineering, three thousand seven hundred and sixty-three rows and one hundred and seventy-two numeric features.

Table~\ref{tab:features_overview} breaks the columns down.

\textbf{Target variable:} \texttt{winner}. The raw data include draws (twenty-four rows); these were \textbf{excluded} so the task is \textbf{binary}: Team~1 win versus Team~2 win. After removal, class proportions are near-balanced (51.05\% Team~1 / 48.95\% Team~2 on three thousand seven hundred and sixty-three rows), so no oversampling or class weighting is required. Labels are encoded as Team~1 $\rightarrow$ \texttt{0} and Team~2 $\rightarrow$ \texttt{1}; confusion matrices and classification reports below follow that convention.

\paragraph{Unit of analysis and limitations of the snapshot.}
Each row represents one professional match with features aggregated or recorded before the match starts (after leakage columns are removed). The dataset does not contain map veto order, server side, or live economy; those omitted factors contribute residual variance and help explain why accuracy stays in a modest band above chance. The twenty-four excluded draws and any rows failing validation leave three thousand seven hundred and sixty-three matches for modelling. Users of the model should treat predictions as conditional on the feature set actually present in \texttt{csgo\_games.csv}, not on full tactical context.

\subsubsection{1.1.2\quad Problem Definition}

\textbf{Task.} Predict the match winner from \textbf{binary} pre-match rows only (Team~1 vs.\ Team~2 after dropping draws).

In practice a model like this is mainly a planning aid: it can suggest who starts as slight favourite or feed internal discussion---it is not presented as something you could trade on. CS matches stay hard to call from pre-match rows alone; important factors simply are not in the table. With balanced classes, \textbf{fifty per cent} is the chance baseline, so \textbf{sixty per cent test accuracy} shows real learning rather than a useless fit. Other tabular pre-match studies in the literature often plateau near \textbf{sixty-five per cent} once authors add neural nets or extra context, which is the right ballpark for what extra data and modelling can buy. The numbers read as probabilities, not as fixed outcomes.

\paragraph{Success criteria and non-goals.}
The coursework mark rests on a defensible pipeline---data handling, exploration, several model families, tuning, and ethics---not on beating every published benchmark that uses different features or modalities. No claim is made that the model is suitable for betting: the accuracy range rules that out. The useful takeaway is which signals move the needle (\texttt{rank\_diff}, team ratings) and how wide the error bars remain.

Outliers were identified via boxplot inspection of key features (e.g., \texttt{rank\_diff}, ratings), right-skewed distributions in world rankings, and domain knowledge---exceptional player performances (e.g., KDR above two) are valid but rare. Median imputation was chosen for robustness to extremes. Range validation confirmed no impossible values (e.g., negative percentages). After imputation, the dataset contains zero missing values.

\paragraph{Alternative imputations considered.}
Means would pull skewed rating tails toward the middle; kNN imputation can leak structure if neighbours are picked before a proper split, so it was not used ahead of the train/test cut. Full multiple imputation is overkill for a single prediction pipeline at this size; a single completed table is reported. Informal checks (subset of columns to zero or mean-fill) nudged test accuracy by under a point---suggesting the bottleneck is signal, not the imputer.

The submission includes \texttt{csgo\_games.csv} and a short note on the cleaning steps.

\paragraph{Leakage control and reproducibility.}
Standings-style point columns that update after the match are dropped before any fit; otherwise the model could cheat. The split is stratified eighty/twenty on \texttt{winner} so neither side is starved in train or test. \texttt{StandardScaler} is fit on train rows only, then applied to test---no test means in the scaler. Routine practice, but worth stating because the headline numbers depend on it.

\subsubsection{1.2.2\quad Feature Engineering and Scaling}

\textbf{Eight engineered features:}

\begin{table}[H]
\centering
\caption{Engineered features and their rationale.}
\begin{tabularx}{\textwidth}{lX}
\toprule
\textbf{Feature} & \textbf{Description and Rationale} \\
\midrule
\texttt{t1\_avg\_rating}, \texttt{t2\_avg\_rating} & Average HLTV rating across each team's five players. Player rating is the primary individual performance metric in professional CSGO. \\
\texttt{t1\_avg\_impact}, \texttt{t2\_avg\_impact} & Average impact score per team, measuring round-winning contributions beyond kills. \\
\texttt{t1\_avg\_kdr}, \texttt{t2\_avg\_kdr} & Average Kill-Death Ratio per team, a standard measure of individual survivability and lethality. \\
\texttt{rank\_diff} & Difference in world rankings (\texttt{t1\_world\_rank} $-$ \texttt{t2\_world\_rank}). Captures the relative competitive strength gap. \\
\texttt{h2h\_advantage} & Difference in head-to-head win percentages. Captures historical team-versus-team performance patterns. \\
\bottomrule
\end{tabularx}
\end{table}

Tournament point columns \texttt{t1\_points} and \texttt{t2\_points} were dropped to prevent \textbf{data leakage}, as they reflect standings updated after matches and would not be legitimate pre-match inputs. All one hundred and seventy-two retained numerical features were standardised using \textbf{StandardScaler}; the target was encoded (\texttt{t1}$\rightarrow$0, \texttt{t2}$\rightarrow$1). The final split is three thousand and ten training samples and seven hundred and fifty-three test samples (stratified eighty/twenty).

\paragraph{Rationale for engineered aggregates.}
Averaging players into team-level stats tracks strength without baking in roster IDs that churn between seasons. \texttt{rank\_diff} and \texttt{h2h\_advantage} describe the \textit{matchup} (``better rank on paper but bad h2h''), not raw ranks in isolation. The engineered block was kept deliberately small: enough signal for logistic regression and trees without a hundred interaction terms.

\subsubsection{1.3.5\quad Potential Biases Identified in the Data}

\begin{enumerate}[leftmargin=1.5em]
    \item \textbf{Temporal Bias:} The dataset spans multiple competitive seasons. CSGO meta-game shifts (strategy, weapon balance, map pool) mean that patterns from earlier years may not generalise to more recent matches.
    \item \textbf{Team Representation Bias:} Top-ranked teams compete more frequently and therefore dominate the dataset. The model may be poorly calibrated for underrepresented lower-ranked or regional teams.
    \item \textbf{Ranking System Bias:} World rankings are a lagging indicator and do not immediately reflect roster changes or strategic pivots, introducing systematic noise in the most predictive feature.
    \item \textbf{Coverage bias:} The sample is weighted toward high-tier international play visible on HLTV; casual or regional events may be underrepresented, so error rates may differ by competition tier.
    \item \textbf{Label definition:} The target is match winner, not round differential or map score; close bo1 upsets and comfortable bo3 wins are treated identically once the match result is recorded.
\end{enumerate}

\paragraph{Link from EDA to modelling choices.}
A line of best fit in rank/rating space already separates winners to some extent; what remains is noise. Logistic regression should therefore stay competitive, forests may add a few points, and very large models cannot invent signal---the inputs omit veto, maps, and same-day form. Single player statistics should not be read as sole drivers when team averages subsume much of the same information.

\subsection{1.4\quad Model Development and Evaluation}

\subsubsection{1.4.1\quad Models Trained}

Three broad model families were trained:

\paragraph{Logistic Regression.} Linear model on the log-odds:
\[
\log\frac{P(y=1|\mathbf{x})}{1-P(y=1|\mathbf{x})}
=
\mathbf{w}^\top \mathbf{x} + b.
\]
It is the obvious first model: fast, inspectable, and probabilistic.

\paragraph{Decision Tree.} Single tree with Gini splits, $G(t) = 1 - \sum_c p(c|t)^2$, \texttt{max\_depth}=10, \texttt{min\_samples\_split}=20 to keep it from memorising. Impurity-based importances come for free.

\paragraph{K-Means.} Required unsupervised check: $k=2$ clusters in feature space, objective $\sum_i \sum_{\mathbf{x} \in C_i} \|\mathbf{x} - \boldsymbol{\mu}_i\|^2$. ARI against true winners is $\approx 0$, so unsupervised geometry does not recover the label---supervised models are doing real work, not picking up a trivial cluster structure.

\paragraph{Heavier models (Figure~\ref{fig:models_accuracy}).}
The experiments also include \textbf{Random Forest} (default and \GridSearchCVname{}-tuned), \textbf{XGBoost}, \textbf{LightGBM}, \textbf{CatBoost}, and \textbf{logistic regression with \texttt{SelectFromModel}} (fifty features from forest importance), plus voting/stacking runs where included in the comparison chart. On the test split \textbf{CatBoost} leads; tuned forests and sparse LR sit underneath. Boosting picks up small non-linearities; nothing approaches ninety per cent because the labels stay noisy.

\subsubsection{1.4.2\quad Evaluation Metrics}

For classification models:

\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Accuracy:} $\frac{TP + TN}{TP + TN + FP + FN}$ --- proportion of correctly classified matches.
    \item \textbf{Precision / recall / F1 (per class):} scikit-learn reports metrics for each label. With encoding \texttt{t1}$\rightarrow$0 and \texttt{t2}$\rightarrow$1, the conventional ``positive'' class in one-vs-rest terms is label~\texttt{1} (Team~2). Precision is $\frac{TP}{TP+FP}$ for that class; recall is $\frac{TP}{TP+FN}$.
    \item \textbf{F1-Score:} harmonic mean of precision and recall for the class of interest; per-class and summary values appear alongside accuracy in the results tables.
\end{itemize}

For K-Means:
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Adjusted Rand Index (ARI):}
    {\small
    \[
    \mathrm{ARI}
    =
    \frac{\mathrm{RI}-\mathbb{E}[\mathrm{RI}]}{\max(\mathrm{RI})-\mathbb{E}[\mathrm{RI}]}
    \]
    }
    where RI is the Rand Index. Agreement between cluster assignments and true labels, corrected for chance. ARI $\approx 0$ indicates random assignment.
    \item \textbf{Silhouette Score:} $s(i) = \frac{b(i) - a(i)}{\max(a(i), b(i))}$, where $a(i)$ is mean intra-cluster distance and $b(i)$ is mean nearest-cluster distance. Values near 1 indicate well-separated clusters.
\end{itemize}

\paragraph{Interpreting the metrics.}
With balanced classes, accuracy is an honest headline; precision and recall per label (\texttt{0}/\texttt{1}) are still examined for asymmetry. F1 compresses that trade-off for the positive class (label~\texttt{1}). For K-Means, ARI scores clusters against \texttt{winner}; silhouette is reported as a geometric sanity check without using labels in the fit.

\paragraph{Naive baselines.}
Two cheap baselines frame Table~\ref{tab:results}. Majority class is $\sim$50\% by construction. \textbf{CatBoost} tops the test set at \textbf{60.96\%}; \textbf{logistic regression on fifty forest-selected features} is the strongest linear result at 58.70\%. With balanced teams, \textbf{fifty per cent} is guessing; landing near \textbf{sixty per cent} indicates repeatable structure in ranks and player aggregates rather than luck. Literature on similar tabular pre-match tasks sometimes reports \textbf{up to about sixty-five per cent} when neural pipelines or richer context are allowed; plain tabular runs often stop short. The observed $\sim$61\% fits that picture---limited by missing veto, map pool, and recent form, not by shallow trees. Errors remain large because pistol rounds, vetoes, and day-of noise are absent from the CSV. Other esports pre-match work often lands in the mid-fifties to mid-sixties; these results fall in the same band. Large gains would require richer inputs rather than another round of boosting tweaks. The PCA plot (Figure~\ref{fig:pca_kmeans}) shows K-Means clusters do not align with winners, so unsupervised geometry does not replace labelled training.

\paragraph{Search design and variance.}
Three-fold CV trades estimate variance against runtime. Random search explores larger boosting spaces without enumerating every grid cell. Some studies also sweep decision thresholds on out-of-fold probabilities (roughly 0.38--0.63) before fixing 0.5 for reporting. CV scores can look optimistic; the ordering on the \textbf{test} split in Table~\ref{tab:results} is taken as authoritative: CatBoost, then sparse LR, then tuned forest.

\paragraph{Linear versus boosted models.}
Sparse logistic regression remains useful when interpretable coefficients matter. CatBoost and tuned forests extract a few more points from the same scaled table by stacking weak splits on player and team stats. The margins look small on a 0--100 scale but matter against a fifty per cent baseline; CatBoost still sits a few points under the $\sim$65\% highs quoted on comparable tasks when tactical inputs are missing. Boosting does not remove randomness---it applies the same leakage-safe columns more aggressively.

\subsubsection{1.4.6\quad Interpretation}

Logistic regression beats the single tree, consistent with many effects being roughly linear after scaling. \textbf{CatBoost} adds a few points by combining weak interactions. Some Kaggle columns (clutch, first-kill rates) look ``post-match flavoured''; they are retained for coursework exploration but would require stricter definitions in production. Matches remain partly random in the manner of live sport rather than deterministic spreadsheet logic. Sixty per cent accuracy is therefore a substantial result against fifty per cent chance, and published ceilings near sixty-five per cent underline how little headroom remains. None of that renders the model suitable for betting; Section~1.5 covers misuse.

\subsubsection{1.4.7\quad Limits of the reported evaluation}

Accuracy and F1 summarise classification quality at a 0.5 threshold; they do not fully describe probability behaviour. Boosting libraries emit calibrated-looking scores in some settings, but tabular match data with overlapping classes can still yield miscalibrated probabilities unless Platt scaling or isotonic regression is fit on held-out data. Stakeholders who care about ranked risk (``top ten matches to watch'') would need calibration checks beyond the confusion matrices shown.

The feature set is also intentionally narrow relative to what a human analyst sees before a match. Map veto order, per-map strength, recent roster moves with only a few games played, and communication-heavy intangibles do not appear in \texttt{csgo\_games.csv}. The models therefore learn from what is available, not from everything that influences a result; the gap between sixty-one per cent and a hypothetical ceiling is partly missing data, not only algorithm choice. Finally, class balance removes the need for class weights in training, which simplifies interpretation but means the pipeline has not been stress-tested on artificially rebalanced samples---an acceptable simplification here, but not if the deployment population shifts toward one-sided matchups.

\subsubsection{1.4.8\quad Plausible extensions (tabular only)}

Within the same tabular setting, several extensions are straightforward to describe even if they were not all implemented end-to-end. Time-based splits and rolling retraining would align evaluation with how odds and rankings actually evolve. Team-ID or roster-ID features could be added with strong regularisation to pool information across seasons without treating every player column as a free parameter. Interaction terms between \texttt{rank\_diff} and head-to-head history could be tested explicitly rather than leaving all interactions to tree ensembles. For transparency, partial dependence or SHAP-style summaries on the CatBoost model would complement impurity and gain-based importances. None of these steps changes the fundamental noise in match outcomes; they mainly tighten estimation and make failure modes easier to audit.

Nested cross-validation would separate hyperparameter selection from final performance estimation more cleanly than a single grid search followed by one test hit. The computational cost rises sharply with boosting grids, which is why the report leans on three-fold CV on the training fold and a single held-out test set for headline reporting. If budgets allow, repeated stratified splits or bootstrap optimism correction would quantify how fragile the two-point gap between CatBoost and logistic regression really is.

\subsection{1.5\quad Ethical Considerations}

\subsubsection{1.5.1\quad Potential Biases}

\paragraph{Temporal and concept drift.}
The rows span several competitive years; patches, maps, and formats shift. A model trained on everything mixes old and new regimes, so the feature-to-label map drifts even when each row looks valid.

\paragraph{Representation and coverage.}
Top teams show up more often, so errors are optimised under a distribution that favours elite play. Lower tiers, smaller regions, or unusual rosters can be under-sampled; probabilities may be off where the data are thin.

\paragraph{Ranking system and lag.}
HLTV-style ranks move slowly. Roster upgrades or a new coach can leave the model looking at stale \texttt{rank\_diff} values exactly when humans are uncertain too.

\paragraph{Data collection and aggregation.}
Public CSVs lean on tier-one LANs and big online leagues; scrims, comms, and morale never appear. Averaging players hides roles (entry vs.\ support) and IGL impact, so identical aggregates can describe different teams in practice.

\subsubsection{1.5.2\quad Mitigation Strategies}

\paragraph{Operational mitigations.}
Models should be retrained on rolling windows, refreshed after major patches, and augmented with short ``form'' windows when data allow. Evaluation should slice by tier or region so one headline accuracy does not hide poor subgroups. Relative features (\texttt{rank\_diff}, rating gaps) usually outperform raw rank integers alone.

\paragraph{Governance and responsible use.}
A simple linear model should remain available alongside CatBoost so failures expose interpretable signs. Any deployment beyond coursework should log predictions and outcomes and review poorly performing slices. Player statistics may constitute personal data in some jurisdictions and warrant the same safeguards as other sensitive fields.

\paragraph{Gambling and misuse.}
The model must \textbf{not} be used for betting. Sixty-one per cent exceeds chance but does not constitute an edge once bookmaker margins and line movement are accounted for. Uncertainty should be communicated when probabilities sit near one half.

\paragraph{Transparency.}
Provenance of the CSV, columns removed, and engineered features should be documented so readers know what the reported scores condition on.

\subsubsection{1.5.3\quad Key Recommendations}

\begin{enumerate}[leftmargin=1.5em]
    \item \textbf{CatBoost} (or \textbf{LR with feature selection} when interpretability dominates) should be used only as decision-support, not as an autonomous decision system.
    \item Models should be \textbf{retrained} on sliding windows of recent matches; post-patch degradation should be monitored.
    \item Metrics should be \textbf{sliced} by team tier, region, and online versus LAN when sample sizes allow.
    \item Model outputs should be \textbf{paired} with human review for roster changes and format changes.
    \item Betting and gambling use cases should be \textbf{prohibited} in product terms; the restriction should be documented for end users.
\end{enumerate}

\paragraph{Closing remarks (Dataset~1).}
Section~1 documents cleaning with leakage removed, a compact engineered block, EDA, linear and tree models with K-Means as a check, tuning tables, and CatBoost leading on the test split. The limitations listed above belong in the main narrative: they mark where the pipeline ceases to be reliable. Together, that constitutes the Dataset~1 contribution of this coursework.

What we hand in alongside this PDF is meant to be rerunnable: the raw CSV, the cleaning code or notebook, the fitted scaler, and any saved models, plus the figure files that appear in the report. Someone could in principle reproduce the tables and plots from those files; the write-up explains the choices, but the numbers ultimately come from running that code. Recording library versions (for example scikit-learn and CatBoost) matters because minor updates can change default behaviour and make old results hard to match.
